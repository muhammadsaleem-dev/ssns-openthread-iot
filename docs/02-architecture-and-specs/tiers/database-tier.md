# Database Tier

## Purpose
The primary role of the database tier within the Smart Monitoring platform architecture is to provide high-throughput, persistent storage for real-time environmental telemetry, dynamic system alerts, mesh network topologies, and node configuration states. MongoDB was selected over traditional relational SQL databases because environmental sensor payloads are dynamic and frequently evolve during hardware prototyping. A schema-less NoSQL document store accommodates these changes without requiring constant, blocking database migrations, while offering exceptional write performance for high-frequency telemetry workloads.

---

## Architectural Overview
The persistence layer relies on a strict **document-oriented architecture**. 
* **Denormalization strategy:** The schema heavily favors denormalization, physically flattening heavy statistical computations (e.g., means, standard deviations) directly into the telemetry document.
* **Embedded documents:** Tightly coupled ephemeral data (like Thread network routes) are aggressively embedded into single documents rather than normalized into separate tables.
* **Soft references:** Relationships between distinct entities are maintained via soft string references rather than rigid relational joins or MongoDB `@DBRef` links.
* **Repository architecture:** Abstraction is achieved through Spring Data MongoDB (`MongoRepository`), which dynamically generates queries.
* **Time-series workload characteristics:** The system operates a one-to-one write strategy (one document per telemetry reading), prioritizing immediate raw write speed over complex, time-bucketed archival compression.

## SensorData Collection
* **Document structure:** Completely flattened architecture to optimize write throughput.
* **Telemetry fields:** Raw vectors stored as `Double` values (`temperature`, `humidity`, `co2`, `tvoc`, `pm2_5`, etc.).
* **Statistical fields:** Pre-computed rolling baseline parameters (`temperatureMean`, `temperatureStd`, etc.) generated by the Edge/Fog tier.
* **Deduplication fields:** Uses `bootId` and `sequenceNumber` to uniquely identify a mesh packet.
* **Timestamp strategy:** Managed inline via Lombok defaults (`Instant.now()`) rather than Spring Auditing.
* **Indexing strategy:** Includes standard indexes on `nodeId` and `timestamp`.

**Compound Index and Exactly-Once Processing (VERIFIED):**
The collection utilizes a `@CompoundIndex(name = "dedup_idx", def = "{'nodeId': 1, 'bootId': 1, 'sequenceNumber': 1}", unique = true)`. This guarantees exactly-once processing at the database level. If a fog node retries the exact same mesh packet due to network latency, MongoDB rejects the duplicate write via a `DuplicateKeyException`, effectively deduplicating the stream without requiring expensive application-level locking.

## Alert Collection
* **Alert types:** Governed by an `AlertType` enumeration (e.g., `TRANSIENT_VOC_EVENT`, `COMBUSTION_WARNING`).
* **Severity levels:** Governed by an `AlertSeverity` enumeration (`INFO`, `WARNING`, `CRITICAL`).
* **Resolution strategy:** Evaluated via a boolean `resolved` field, determining if an alert is active or historical.
* **Context storage:** An unstructured `context` string field stores JSON-stringified debug metadata.
* **Self-healing mechanism:** The heuristic engine continuously queries for unresolved alerts and flags them `resolved=true` if telemetry returns to normal boundaries. (Status: VERIFIED)

## SensorNode Collection
* **Node registration:** Uses a unique `@Indexed` logical hardware ID (often MAC/FICR).
* **Connectivity state:** Tracks operational health via a `NodeStatus` enumeration and `lastSeenAt` timestamp.
* **Configuration storage:** Manages properties sent down to the edge (e.g., `baselineWindowSize`).
* **ML parameters:** Tracks boolean toggles and tuning limits (e.g., `forecast_horizon_min`).
* **Timestamp management:** Uses inline defaults (`registeredAt = Instant.now()`). (Status: VERIFIED)

## NetworkTopology Collection
* **Gateway metadata:** Tracks the border router identifier via `gatewayId`.
* **Thread routing information:** Stores active OpenThread paths.
* **Embedded structures:** Heavily utilizes embedded arrays rather than relational tables.
* **Topology snapshots:** The collection effectively acts as a snapshot store, tracking the latest state using `lastUpdatedAt`. (Status: VERIFIED)

## Relationships
* **Soft references:** Relationships between distinct entities are maintained strictly via soft strings (e.g., `SensorData.nodeId` points to `SensorNode.nodeId`).
* **Absence of DBRef:** MongoDB `@DBRef` links are completely absent.
* **Absence of joins:** The schema design eliminates the need for database-level joins.
* **Rationale:** By decoupling collections, the database prevents cross-collection locking during high-frequency inserts, maximizing telemetry ingestion speed. (Status: VERIFIED)

## Repository Layer
* **SensorDataRepository:** Handles high-volume time-series querying and limits queries using explicit methods like `findTop400ByOrderByTimestampDesc`.
* **AlertRepository:** Focuses heavily on state-machine lookups (e.g., `findFirstByNodeIdAndTypeAndResolvedFalse`).
* **SensorNodeRepository:** Manages singleton queries based on unique logical IDs (`findByNodeId`).
* **NetworkTopologyRepository:** Retrieves the latest snapshot (`findFirstByOrderByLastUpdatedAtDesc`).
* **Filtering, Sorting, and Pagination:** Heavily leverages Spring Data derived queries (e.g., `OrderByTimestampDesc`) and relies on `Pageable` parameters to return managed `Page<T>` objects. (Status: VERIFIED)

---

## Query Patterns
* **Latest telemetry retrieval:** Real-time dashboards execute continuous requests for `findTop400ByNodeIdOrderByTimestampDesc`.
* **Historical queries:** Range analytics leverage `findByTimestampBetween`.
* **Alert lookups:** Evaluated continuously during ingestion to determine heuristic state escalations.
* **Duplicate detection:** Handled blindly via MongoDB `DuplicateKeyException` bounds checking.
* **Topology updates:** Executed periodically as atomic document replacements.
* **Offline node detection:** Background schedules sweep `nodes` to verify `lastSeenAt` staleness. (Status: VERIFIED)

---

## Transactions and Consistency
* **Document-level atomicity:** MongoDB natively guarantees atomic writes at the single-document level. Since the schema uses flattened and embedded models, atomicity is maintained without complex orchestration.
* **Last-write-wins strategy:** The application utilizes MongoDB's default behavior for handling concurrency.
* **Absence of optimistic locking (VERIFIED):** The Spring Data `@Version` annotation is completely missing, indicating no protection against dirty reads.
* **Absence of transactions (VERIFIED):** There are no `@Transactional` contexts implemented across the backend tier.

---

## Performance Optimization
* **Flattened schema design:** Accelerates inserts by bypassing relational integrity checks.
* **Edge-side aggregation:** Offloads statistical mathematical computations to microcontrollers, bypassing expensive MongoDB aggregation pipelines.
* **Indexing:** Optimizes read-heavy charting routes.
* **Deduplication:** Utilizes unique compound indexes to reject invalid packets instantly at the C++ driver level, protecting Java heap space. (Status: VERIFIED)

---

## Failure Scenarios
* **Duplicate packets:** Safely rejected by the `dedup_idx` unique compound index.
* **Database failures:** Results in `DataAccessException`, triggering a 500 API response, which forces the Fog gateway to buffer and retry.
* **Corrupted payloads:** Blocked at the Controller layer by `@Valid` JSR-380 constraints prior to reaching the database.
* **Node failures:** Identified by scheduled sweeps checking `lastSeenAt` timeouts.
* **Concurrent writes:** Blindly overwrite each other due to the missing `@Version` optimistic lock constraint. (Status: VERIFIED)

---

## Scalability Analysis
* **Write-heavy workloads:** Well supported initially, but individual `save()` calls will saturate standard connection pools at scale.
* **Memory consumption:** The `NetworkTopology` array grows unboundedly with mesh size, risking document reallocation overhead.
* **Connection management:** Vulnerable to Thread pool exhaustion during sudden node reconnection surges.
* **WebSocket pressure:** Serialized telemetry forces high heap allocations during concurrent broadcasting.
* **Long-term storage growth:** Continuous uncompressed 1Hz ingestion without TTL indexes will result in critical disk exhaustion. (Status: INFERRED)

---

## Limitations
* **Missing TTL indexes:** No automatic pruning mechanism exists for historical data. (NOT FOUND)
* **Missing caching:** Configuration state is not cached in Redis, resulting in redundant database reads. (NOT FOUND)
* **Missing bulk operations:** Telemetry is written sequentially rather than utilizing batch `saveAll()` mechanisms. (NOT FOUND)
* **Missing time-series collections:** Telemetry uses standard uncompressed document collections. (NOT FOUND)
* **Missing optimistic locking:** Concurrent writes risk state corruption. (NOT FOUND)

---

## Future Improvements
* **Kafka:** Introduce a message broker to absorb and buffer massive ingestion spikes, protecting the Spring Boot thread pool.
* **Redis:** Cache physical node configurations to eliminate repetitive database reads.
* **MongoDB Time-Series Collections:** Migrate `sensor_data` to native Time-Series format for drastic disk compression.
* **Bulk insertion:** Refactor the Fog tier to batch telemetry (e.g., 50 readings per POST) to slash IOPS.
* **Archival strategies:** Implement cold-storage offloading (AWS S3) and TTL indexes for aggressive hot-store pruning.

---

## Conclusions
The Smart Monitoring platform effectively implements a high-throughput, denormalized NoSQL database architecture. The flattened design, complete absence of `@DBRef` relational joins, and strict reliance on document-level atomicity maximize ingestion speeds for environmental telemetry. A clever compound index guarantees exactly-once processing, protecting the system from mesh network duplication. However, the system currently lacks time-series compression, bulk ingestion, caching layers, and TTL pruning, making it vulnerable to long-term storage exhaustion and sudden connection spikes. Addressing these limitations is essential before executing a large-scale enterprise deployment.
