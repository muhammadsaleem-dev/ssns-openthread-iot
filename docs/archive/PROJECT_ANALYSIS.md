## 1. Executive Summary

### Project Purpose
The Smart Sensor Network System (SSNS) is a **Thread-based intelligent indoor environmental monitoring platform** that combines low-power OpenThread mesh networking with edge-native machine learning anomaly detection and forecasting. The system provides operators with multi-variable environmental insights while maintaining offline-first resilience.

### Target Users
- **Facility Operators:** Monitor environmental conditions (temperature, CO2, humidity, particulates, VOCs) across indoor spaces
- **Facility Managers:** Evaluate air quality trends and respond to anomalies
- **System Administrators:** Manage distributed sensor nodes, configure thresholds, and monitor infrastructure health

### Core Objectives
1. **Real-time Environmental Monitoring:** Collect multi-dimensional sensor data every 30 seconds via CoAP over Thread
2. **Intelligent Anomaly Detection:** Identify subtle multi-variable environmental anomalies using Isolation Forest (unsupervised learning)
3. **Proactive Forecasting:** Predict future threshold breaches using sliding-window linear regression (30-minute horizon)
4. **Explainable AI:** Provide context-aware interpretable alerts that explain which environmental parameters drove the anomaly
5. **High Availability:** Operate offline-first with automatic failover between distributed fog nodes
6. **Edge-Native Processing:** Keep ML inference local (no cloud dependency) while maintaining low computational overhead

### Key Capabilities (Verified Implemented)
- ✅ Multi-node Thread mesh topology discovery and visualization
- ✅ Per-node Isolation Forest baseline learning (24-hour rolling window)
- ✅ Real-time anomaly scoring with feature attribution
- ✅ CO2 and PM2.5 proactive forecasting (30-minute horizon)
- ✅ Four-tier alert model (deterministic, behavioral, predictive, infrastructure)
- ✅ Automatic node registration and last-seen tracking
- ✅ WebSocket real-time telemetry streaming
- ✅ Node offline detection and alerting
- ✅ Hardware fault detection via health status bitmask
- ✅ Distributed Redis-backed deduplication
- ✅ Load-balanced dual-API architecture (Nginx)

### 2.5 Networking Architecture

**Wireless Protocol:** OpenThread (802.15.4 IPv6 mesh)  
**Application Protocol:** CoAP (Constrained Application Protocol) with CONFIRMABLE messages

**Thread Mesh Configuration:**
- **PAN ID:** Configured in `.env` (WSN01)
- **Extended PAN ID:** `OT_EXTPANID` (6-byte identifier)
- **Active Timestamp:** Fixed at `2000000000` (year 2033) to prevent replay rejection
- **Network Key:** Pre-compiled into sensor firmware; no commissioner phase
- **Mesh Prefix:** `fd5e:a726:ec55:ee12::/64`

**Anycast Routing:**
- Sensor nodes transmit to ALOC (Anycast Locator) address: `fd5e:a726:ec55:ee12::1`
- Multiple Fog Nodes (OTBR instances) advertise the same prefix on their respective Border Router interfaces
- Thread mesh automatically routes packets to the nearest healthy Border Router

**Gateway Ingestion Pipeline:**
1. **OTBR (OpenThread Border Router)** receives 802.15.4 frames from sensor nodes
2. **Python Gateway** (aiocoap CoAP server) listens on UDP port 5683
3. **Redis Queuing** deduplicates packets and buffers them locally
4. **HTTP Forwarder** POSTs to Spring Boot backend with exponential backoff retry
5. **MongoDB Persistence** stores deduplicated telemetry with compound unique index

**Gateway Redundancy (HA):**
- Mac/Linux Fog Node: `socat` TCP bridge for Docker VM boundary crossing
- Windows Fog Node: Direct USB passthrough via WSL2 `usbipd`
- Both Fog Nodes sync `.env` to use identical Thread network credentials
- Sensor nodes automatically fail over between Border Routers via ALOC routing

### 2.6 Thread/OpenThread Deep Dive

**OTBR (OpenThread Border Router) Role:**
- Bridges 802.15.4 mesh to IPv6 network (UDP port 5683 for CoAP)
- Runs RCP (Radio Co-Processor) firmware on nRF52840 hardware
- Exposes OTBR Web GUI (port 8080) for Thread network diagnostics
- Manages dataset (network credentials, timestamps, keys)

**Thread Network Topology Tracking:**
- Backend polls thread/routes via OTBR HTTP API or receives updates from gateway
- [NetworkTopology model](../platform/api/src/main/java/de/iot/smartmonitoring/model/NetworkTopology.java) stores latest snapshot
- Includes gateway health status (signal strength, frame error rate)
- Contains list of [ThreadRouteNode](../platform/api/src/main/java/de/iot/smartmonitoring/model/ThreadRouteNode.java) objects with role (Leader, Router, EndDevice)

**Leader Detection:**
- Thread mesh elects a Leader node dynamically
- Leader role tracked in topology data
- Backend identifies leader by highest sequence number or role flag

**Router vs End Device:**
- **Routers:** Can forward packets, maintain parent relationships
- **End Devices:** Battery-powered, attach to routers
- Topology shows parent-child relationships for mesh visualization

**Network Diagnostics:**
- [GatewayHealth model](../platform/api/src/main/java/de/iot/smartmonitoring/model/GatewayHealth.java) tracks:
  - Radio channel (1-26)
  - TX power
  - Frame error rate
  - Partition ID (multi-partition detection)

**Topology Visualization:**
- [NetworkTopologyPage](../platform/dashboard/src/pages/NetworkTopologyPage.jsx) renders interactive graph
- Nodes colored by role (Blue=Leader, Green=Router, Gray=EndDevice)
- Parent-child links show mesh structure
- Manual refresh button polls backend for latest state

## 7. ML / Intelligence Deep Dive

### 7.1 ML Architecture Overview

**ML Service Location:** [platform/ml-service](../platform/ml-service)  
**Language:** Python 3.12 with FastAPI  
**Core Components:**
- [ml_engine.py](../platform/ml-service/app/ml/ml_engine.py): IsolationForest detector manager
- [forecaster.py](../platform/ml-service/app/ml/forecaster.py): Linear regression forecaster
- [poller.py](../platform/ml-service/app/services/poller.py): Async polling loop that fetches latest telemetry and scores it
- [main.py](../platform/ml-service/app/main.py): FastAPI app with `/analyze` and `/status` endpoints

**ML Service Deployment:**
- Runs as separate Docker container (port 8000, internal only)
- Polls backend every 15 seconds (configurable: `POLL_INTERVAL_SECONDS`)
- Runs anomaly detection and forecasting on latest per-node readings
- Creates alerts in backend via POST to `/api/alerts`
- Maintains per-node detector and forecaster instances in memory

### 7.2 Anomaly Detection Engine

**Algorithm:** Isolation Forest (scikit-learn)  
**Class:** [AnomalyDetector](../platform/ml-service/app/ml/ml_engine.py)

**Input Features (10-dimensional):**
1. Temperature (°C)
2. Humidity (%)
3. CO2 (ppm)
4. TVOC (ppb)
5. eCO2 (ppm)
6. PM1.0 (µg/m³)
7. PM2.5 (µg/m³)
8. PM4.0 (µg/m³)
9. PM10 (µg/m³)
10. Light Intensity (lux)

**Baseline Learning Phase:**
- Collects first `baseline_window_size` readings (default: 20) without scoring
- Once threshold reached, trains IsolationForest on baseline data
- Sets `is_fitted = True` and begins real-time anomaly detection
- No alerts triggered during calibration; deterministic thresholds remain active

**Real-Time Scoring:**
- For each new telemetry: predict anomaly status (`-1` = anomaly, `1` = normal)
- Extract anomaly score (decision function value)
- Rank feature deviations (Z-score from baseline mean) to identify top 2 drivers
- Generate explainable context string and recommended action

**Contamination Parameter:**
- Sensitivity (1-100) maps to contamination (0.01-1.0)
- Default sensitivity: 5 → contamination 0.05 (5% expected anomalies)
- Operator can adjust via PUT `/api/nodes/{nodeId}/ml/config?sensitivity=X`

**Model Persistence:**
- Trained models saved to disk (joblib format): `/tmp/ble_ml_models/isolation_forest_{nodeId}.pkl`
- On ML service restart: restores persisted models (no warm-up required)
- New nodes start with fresh unfitted models

**Drift Handling:**
- Rolling 24-hour baseline window implemented at **policy level** (not in current code)
- Currently uses initial 20-reading baseline without automatic expiration
- Recommendation: Add timestamp-based window rotation for long-running deployments

### 7.3 Forecasting Engine

**Algorithm:** Sliding Window Linear Regression  
**Class:** [LightweightForecaster](../platform/ml-service/app/ml/forecaster.py)

**Input Features (2-dimensional):**
- CO2 (ppm)
- PM2.5 (µg/m³)

**Forecast Horizon:**
- Default: 1800 seconds (30 minutes)
- Configurable per-node: `nodes.forecast_horizon_min`

**Sliding Window:**
- Maintains rolling history of up to 60 readings (configurable: `history_size`)
- Each entry: (timestamp_sec, co2, pm2_5)

**Linear Regression Method:**
- Computes least-squares line fit: `y = mx + c`
- Applies to both CO2 and PM2.5 independently
- Extrapolates to `latest_time + horizon_sec`

**Forecast Output:**
- Projected CO2 (ppm) and PM2.5 (µg/m³) at horizon endpoint
- Per-minute slope (m * 60) for trend visualization
- Context string: `"Projection in 30m | CO2: 1650 ppm (+2.5/min) | PM2.5: 40 µg/m³ (+0.15/min)"`
- Recommended action based on which parameter will breach threshold

**Threshold-Crossing Logic:**
- If projected CO2 > 1500 ppm AND PM2.5 > 35 µg/m³: "Proactively increase ventilation and check air filters"
- If projected CO2 > 1500 ppm only: "Proactively increase fresh air intake"
- If projected PM2.5 > 35 µg/m³ only: "Proactively check air filters"

**Requirements for Forecasting:**
- Minimum 10 readings in history (to avoid under-fit)
- All readings must have valid (non-fault) values
- Returns (None, None, None, None) if insufficient data

### 7.4 Explainable AI (XAI) Layer

**Context Generation:**
Upon anomaly detection, ML service computes:
1. **Anomaly Score:** Decision function output (negative = more anomalous)
2. **Feature Deviation Ranking:** Sort features by Z-score deviation from baseline mean
3. **Top 2 Drivers:** Identify which 2 parameters most deviate from normal
4. **Percentage Change:** Calculate `((value - mean) / abs(mean)) * 100` for each driver
5. **Feature Name Mapping:** Map to human-readable labels (Temp, CO2, PM2.5, etc.)

**Recommended Action Logic:**
- If top driver is Temperature: "Inspect HVAC unit"
- If top driver is CO2: "Increase ventilation or open windows"
- If top driver contains "PM": "Check building air filters; keep external windows closed"
- If top driver is "VOC": "Investigate for chemical spills or off-gassing"
- Default: "Perform general environmental inspection"

**Example Alert Context:**
```
Anomaly score: 2.34 | Key drivers: CO2 (+45% vs baseline), PM2.5 (+30% vs baseline)
Recommended Action: Increase ventilation or open windows.
```

### 7.5 ML Poller Loop

**File:** [poller.py](../platform/ml-service/app/services/poller.py)

**Execution:** Async background task running every `POLL_INTERVAL_SECONDS` (default: 15 seconds)

**Workflow:**
1. GET `/api/nodes` to discover active nodes
2. For each node:
   - Skip if `mlEnabled == false`
   - GET `/api/sensor-data/latest/{nodeId}` (1 reading)
   - Apply **Guard 1:** Skip if timestamp already processed (dedup)
   - Apply **Guard 2:** Check anomaly alert cooldown (60-second per-node)
   - Apply **Guard 3:** Check forecast alert cooldown (60-second per-node)
   - Extract 10-dimensional feature vector
   - Check for hardware faults (-999.0 placeholders) and skip if present
   - Run `detector_manager.process()` to score anomaly
   - If anomaly: POST alert to `/api/alerts`
   - Run `forecaster_manager.process()` to compute 30-minute forecast
   - If forecast triggers threshold: POST forecast warning alert

**Deduplication Strategy:**
- **Guard 1 (Timestamp dedup):** `last_processed_timestamps[node_id]` to avoid re-scoring same reading
- **Guard 2 (Anomaly cooldown):** `last_alert_time[node_id]` — no ML_ANOMALY alerts within 60 seconds
- **Guard 3 (Forecast cooldown):** `last_forecast_alert_time[node_id]` — no FORECAST_WARNING alerts within 60 seconds

**HTTP Client:** httpx async with 10-second timeout

### 7.7 Current ML Limitations (Verified)

| Limitation | Impact | Workaround/Future Plan |
| --- | --- | --- |
| **Fixed 20-reading Baseline** | Does not adapt to seasonal changes | Implement rolling 24-hour window with timestamp-based rotation |

| **No Sensor Drift Correction** | Does not account for aging or miscalibration of sensors | Manual baseline reset available; auto-recalibration could use cross-node comparison |
| **No Online Learning** | Models don't retrain continuously; only on manual reset | By design for stability; online learning could cause erratic behavior |

## 8. Architecture Strengths

1. **Offline-First Resilience:** Fog nodes buffer telemetry in Redis with exponential backoff; system continues operating if backend is unreachable
2. **Low-Power Wireless Mesh:** OpenThread CoAP provides 802.15.4 mesh with self-healing routing; sensor nodes run on battery without excessive drain
3. **Edge-Native ML:** IsolationForest and linear regression run locally; no cloud dependency; sub-second anomaly scoring
4. **Explainable AI:** Feature attribution explains anomalies to operators; not a black-box system
5. **Multi-Tier Alerting:** Four-layer alert model (deterministic, behavioral, predictive, infrastructure) reduces false positives and provides context
6. **High Availability:** Dual API instances behind Nginx load balancer; distributed fog nodes with automatic failover via Thread ALOC routing
7. **Distributed Deduplication:** Redis-backed dedup at gateway layer prevents duplicate storage; compound MongoDB index provides fallback
8. **Automatic Node Registration:** Unknown nodes auto-register on first telemetry; zero manual provisioning required
9. **Hardware-Agnostic Firmware:** Node IDs derived from MAC addresses; same firmware binary works on unlimited sensor nodes
10. **Extensible Gateway Pattern:** Strategy pattern allows easy swap from simulator to real sensors; no backend/frontend changes needed
11. **Real-time WebSocket Streaming:** Dashboard receives live telemetry updates; no polling latency
12. **Rich API Documentation:** OpenAPI 3.0 / Swagger UI for easy integration

---

## 9. Architecture Weaknesses

1. **No Authentication/Authorization:** System assumes trusted internal network; no multi-tenant isolation or role-based access control
2. **Single Database Instance:** MongoDB not replicated; single point of failure (mitigation: backup volumes)
3. **Monolithic Data Schema:** All telemetry stored in single collection; no time-series partitioning (future: TimeSeries collections in MongoDB 5.0+)
4. **Limited Historical Topology:** Only latest Thread mesh snapshot stored; no historical comparison or topology evolution tracking
5. **Forecast Alert Auto-Resolve Disabled:** Forecast alerts require manual resolution; no auto-clearing when trend reverses
6. **No Sensor Validation:** Assumes calibration trust; no cross-sensor consistency checks or plausibility bounds
7. **Baseline Learning Hard-Coded:** 24-hour rolling window not implemented; uses fixed 20-reading initial baseline only
8. **No Graceful Degradation for ML:** If ML service crashes, anomaly detection stops (system still runs deterministic thresholds)
9. **Tight Coupling to MongoDB:** No abstraction layer; schema changes require API and ML service updates
10. **No Data Retention Policy:** All telemetry stored indefinitely; MongoDB will grow unbounded without TTL or archival strategy
11. **No Audit Logging:** Alert resolution and configuration changes not logged; no compliance trail
12. **Dashboard Runs Unencrypted HTTP:** No TLS/SSL; assumes internal network only

---

## 10. Technical Debt

1. **Missing Unit Tests:** Minimal test coverage for ML engine, alert service, and gateway
2. **No Integration Tests:** E2E flows (ingest → ML scoring → alert creation) not tested
3. **Hardcoded Thresholds:** Alert thresholds in AlertService hard-coded in `application.yml`; should move to configurable per-node thresholds
4. **Simulator Hardcoded to Gaussian Drift:** Telemetry simulator generates predictable random walks; should support JSON-based test scenarios
5. **No Circuit Breaker:** ML service and backend don't gracefully degrade if network is flaky; exponential backoff but no hard circuit break
6. **Documentation Fragmented:** Architecture explained in multiple .md files; no single source of truth
7. **Swagger Tags Incomplete:** API endpoints have `@Tag` annotations but not systematically organized
8. **WebSocket Broadcast Unoptimized:** All clients receive all telemetry; should filter by subscribed nodes
9. **Gateway CBOR Encoding Fragile:** Manual array parsing; no schema versioning for protocol evolution
10. **ML Model Serialization Non-Portable:** joblib pickle files; not human-readable; limited versioning strategy
11. **Thread Network Hardcoded Values:** Mesh timestamps and credentials hard-coded in firmware; no dynamic provisioning
12. **No Metrics for ML Accuracy:** No tracking of false positive rate, recall, or precision for Isolation Forest model
